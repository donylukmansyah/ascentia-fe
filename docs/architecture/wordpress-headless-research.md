# WordPress as Ascentia's Headless Content Backend

## Scope and evidence

This note compares the official WordPress REST API and WooCommerce Store API for the frontend's documented content needs. **Documented behavior** below is from the linked WordPress and WooCommerce references; **live observations** are from a point-in-time, unauthenticated public GET/CORS probe of Ascentia's site; **recommendations** are implementation guidance for this repository. Public responses can vary with content changes, plugins, permissions, and site configuration. The probe did not inspect WordPress admin settings or verify the deployed frontend origin.

## Documented behavior

- **WordPress content and media:** The core REST API exposes posts at `/wp/v2/posts`, pages at `/wp/v2/pages`, and media at `/wp/v2/media`. The post/page schemas include content, title, excerpt and featured-media IDs; media records include `source_url`, `alt_text`, captions and media details. These are suitable core resources for blog entries, pages and attachment metadata. [Posts](https://developer.wordpress.org/rest-api/reference/posts/) · [Pages](https://developer.wordpress.org/rest-api/reference/pages/) · [Media](https://developer.wordpress.org/rest-api/reference/media/)
- **Products:** WooCommerce's **Store API** is specifically a public, unauthenticated API for customer-facing product, cart and checkout functionality. Its product endpoints are `/wp-json/wc/store/v1/products` and `/products/:id` (including slug lookup); listed fields include prices, descriptions, images, stock/purchase state, categories and product attributes. Draft and otherwise unpublished products are excluded. The endpoint documents search, category, attribute, price, stock, ordering and other filters. [Store API overview](https://developer.woocommerce.com/docs/apis/store-api) · [Products endpoint](https://developer.woocommerce.com/docs/apis/store-api/resources-endpoints/products)
- **Different trust boundaries:** Store API requests need no API keys and do not expose sensitive store settings or other customers' data; its responses may reflect the current customer and WooCommerce uses cookie-based customer sessions. It cannot administer store settings or retrieve other customers' orders. Store API writes to supported cart/checkout resources are a separate customer-facing capability; endpoints that permit writes may require a nonce. In contrast, WordPress REST API authenticated management actions require authentication and appropriate capabilities. WordPress documents cookie authentication with REST nonces for logged-in same-site use and Application Passwords over HTTPS for remote REST use. [Store API overview](https://developer.woocommerce.com/docs/apis/store-api) · [WordPress REST authentication](https://developer.wordpress.org/rest-api/using-the-rest-api/authentication/)
- **Pagination and filters:** WordPress REST collection endpoints support `page`, `per_page` (maximum 100), and `offset`; paginated responses include `X-WP-Total` and `X-WP-TotalPages`. Core posts/pages document search, date, include/exclude and ordering filters. WooCommerce Store API collections also use `page` and `per_page` (maximum 100) and return total-count/page headers plus `Link` pagination links; supported product filters are endpoint-specific and listed in the Products reference. [WordPress pagination](https://developer.wordpress.org/rest-api/using-the-rest-api/pagination/) · [Posts](https://developer.wordpress.org/rest-api/reference/posts/) · [Pages](https://developer.wordpress.org/rest-api/reference/pages/) · [Store API overview](https://developer.woocommerce.com/docs/apis/store-api) · [Products endpoint](https://developer.woocommerce.com/docs/apis/store-api/resources-endpoints/products)
- **Caching/freshness:** The cited API references describe pagination, response data, and (for Store API) customer/session behavior, but do not establish one cache lifetime or freshness guarantee for every endpoint or installation. Store API data can depend on the current customer, and password-protected products have cookie-dependent description visibility. [Store API overview](https://developer.woocommerce.com/docs/apis/store-api) · [Products endpoint](https://developer.woocommerce.com/docs/apis/store-api/resources-endpoints/products)

## Live Ascentia endpoint observations

The following are direct observations from a point-in-time, unauthenticated public probe; they describe only the responses sampled, not the site's admin configuration or a guarantee of current/future content.

- **REST root and pages:** [`https://ascentia.co.id/wp-json/`](https://ascentia.co.id/wp-json/) returned JSON identifying the site as Ascentia, with `page_on_front: 86`, `show_on_front: "page"`, and namespaces including `wp/v2` and `wc/store/v1`. The sampled [pages collection](https://ascentia.co.id/wp-json/wp/v2/pages?per_page=10&_fields=id,slug,status,parent,link,modified,title,excerpt,featured_media) included published page ID 86 (`home`, modified `2025-03-10`) and page ID 73 (`articles`), along with Products, Cart, Checkout and other pages. The [front-page record](https://ascentia.co.id/wp-json/wp/v2/pages/86?_fields=id,slug,modified,title,content) returned 80,440 characters in `content.rendered`, including Divi `et_pb_` shortcodes; treat that field as page-builder output, not a stable structured content contract for the new frontend.
- **Articles/posts:** The [posts collection](https://ascentia.co.id/wp-json/wp/v2/posts?per_page=20&_fields=id,date,modified,slug,status,link,title,excerpt,featured_media,categories,tags) returned one published item: the default `Halo dunia!` post, modified `2022-08-01`, in category ID 1. The [category 20 query](https://ascentia.co.id/wp-json/wp/v2/posts?categories=20&per_page=20&_fields=id,date,modified,slug,status,link,title,excerpt,featured_media,categories,tags) returned an empty array. The [Articles page response](https://ascentia.co.id/wp-json/wp/v2/pages?slug=articles&_fields=id,slug,modified,title,excerpt,content,featured_media,link) had page ID 73 and `content.rendered` containing Divi builder shortcodes such as `et_pb_section` and `et_pb_blog` (`include_categories=20`), rather than a clean article-feed schema.
- **Store API catalog:** The public [Store API product collection](https://ascentia.co.id/wp-json/wc/store/v1/products?per_page=3) returned product objects including slugs, HTML descriptions, prices, images (`src`, `srcset`, `sizes`, `alt`), categories, and purchase flags such as `is_purchasable`; sampled products included TGA 1100 and Phoenix models. A one-product request returned HTTP 200 with `X-WP-Total: 9` and `X-WP-TotalPages: 9`, indicating nine items in that sampled collection response. A [category-filtered query](https://ascentia.co.id/wp-json/wc/store/v1/products?category=55&per_page=2&_fields=id,name,slug,categories) returned products matching XRF Scientific category ID 55; the [categories endpoint](https://ascentia.co.id/wp-json/wc/store/v1/products/categories?per_page=10) showed that category in a hierarchy. The [brands endpoint](https://ascentia.co.id/wp-json/wc/store/v1/products/brands?per_page=20) returned `[]`, and the [attributes endpoint](https://ascentia.co.id/wp-json/wc/store/v1/products/attributes?per_page=20) returned one `Spectral Evolution` attribute with count 0.
- **Sample commercial fields:** In a request selecting `id,name,slug,prices,brands,categories,is_purchasable,images`, the first three sampled products had `prices.price: "0"`, `currency_code: "USD"`, `brands: []`, and `is_purchasable: false`. This sample is not evidence that all nine products share those values; it does mean price and brand data require business validation before being treated as customer-ready.
- **CORS:** For a request to the [Store API product endpoint](https://ascentia.co.id/wp-json/wc/store/v1/products?per_page=1), a GET carrying `Origin: http://localhost:3000` returned HTTP 200, `Vary: Origin`, and the total headers above, but no `Access-Control-Allow-Origin`. An OPTIONS preflight for that localhost origin returned HTTP 200 with `Access-Control-Allow-Origin: http://localhost:3000`. Separately, browser `window.fetch` from `https://example.com` to the Store API failed with `TypeError: Failed to fetch`. These observations are inconsistent and neither origin is established here as the deployed frontend origin; they do not establish that browser access works for the actual app.

### Implications for this repository

- **Start with the WooCommerce Store API for the dynamic catalog.** The sampled public product collection and category filter demonstrate a usable public read path for products. Public Store API reads do not require WooCommerce consumer credentials; do not add keys to browser code. The repo README documents `VITE_WP_API_BASE_URL=https://ascentia.co.id/wp-json` and `VITE_WC_API_BASE_URL=https://ascentia.co.id/wp-json/wc/store/v1`, but `src/` currently has no WordPress fetch/client references and `/products`, `/blogs`, and `/news` are heading-only placeholders. The existing `sanitize-html` dependency can be used to sanitize HTML descriptions before rendering.
- **Clarify the CMS publishing model before wiring blog or homepage content.** The sampled core posts endpoint did not supply the expected article feed, while the Articles page and front-page content contain Divi shortcodes. Do not treat the one-post result as proof that articles do not exist elsewhere, or parse Divi shortcodes as a stable content model; confirm where and how content is published and which REST-visible fields/post type/taxonomy should serve it.
- **Validate product business semantics.** Do not assume sampled zero prices, USD currency, empty brands, or non-purchasable flags are display-ready or apply to every product; confirm intended pricing/brand behavior with the content/store owner before designing catalog presentation.
- **Resolve browser access at the real origin.** Test requests in a browser from the actual deployed frontend origin. If CORS does not permit it, use an appropriate server-side fetch path or deliberately configure WordPress CORS for the required origin; the localhost OPTIONS response alone is not proof that frontend GETs work.

These observations complement, rather than replace, the generic WordPress and WooCommerce API behavior and security guidance above. The sampled public GETs do not inspect admin settings, verify production frontend deployment/origin, or establish a stable guarantee about content, headers, or configuration.

## Repo-specific recommendation

**Recommendation:** Use the WooCommerce Store API for the public product catalog, and the core WordPress REST API for public pages and media metadata. Although core posts are a standard API resource, the sampled posts endpoint did not provide a real article feed; clarify the site's publishing model before using it for blog/news pages. This matches the repository's intended base URLs/endpoints in [`README.md`](../../README.md): `https://ascentia.co.id/wp-json`, `https://ascentia.co.id/wp-json/wc/store/v1`, and `/products`. Build a small frontend data layer around the public read endpoints, request only needed fields/filters, paginate rather than downloading whole collections, and render image URLs (and responsive image data when present) from returned records.

The current `src/` contains no WordPress API client or WordPress API references, so the README describes intended integration rather than an integration currently present in source. Do not put WooCommerce consumer credentials, WordPress passwords, or other privileged credentials in `VITE_*` variables: browser-exposed frontend configuration is not a secret. If a future feature needs privileged WordPress/WooCommerce management access, keep credentials and authenticated requests in a server-side component and grant only the required capabilities. The public Store API is the appropriate catalog read interface, not a reason to publish REST API consumer credentials. [Store API overview](https://developer.woocommerce.com/docs/apis/store-api) · [WordPress REST authentication](https://developer.wordpress.org/rest-api/using-the-rest-api/authentication/) · [Vite env variables and modes](https://vite.dev/guide/env-and-mode/)

For implementation, confirm which post type/taxonomy is intended to supply articles, validate product fields such as price and brand with the business owner, and test browser CORS from the actual frontend origin; this probe did not verify any of those implementation requirements. Treat cache policy as deployment-specific: inspect actual cache headers/CDN behavior and avoid shared caching of customer/session- or password-dependent responses unless correctly varied. The live observations establish only the sampled public responses; they do not establish broader endpoint availability, plugin-added fields/filters, permissions, headers, current admin settings, or deployed-origin behavior.
